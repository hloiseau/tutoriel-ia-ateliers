# Missions sur le PC de l’auteur

Le point d’entrée est [LOCAL-COORDINATEUR.md](../LOCAL-COORDINATEUR.md). Ces modules donnent les vérifications propres à chaque atelier. Pour ne reprendre qu’un module, fournir aussi le prompt coordinateur : ses règles de préparation et de preuve restent applicables.

| Mission | Ce qui manque principalement | Intervention de Hugo |
| --- | --- | --- |
| [2 — Apprentissage](02-apprentissage.md) | Reprise sur son système, page de dessin dans un navigateur réel | Seulement si le navigateur n’est pas pilotable |
| [3 — Modèle local](03-modele-local.md) | Mesures CPU/GPU comparables sur sa machine | Aucune en principe |
| [4 — Développement](04-developpement.md) | Résolution par un assistant réel et manipulations d’interface | Connexion ou interface si inaccessible à l’assistant |
| [5 — Agents](05-agents.md) | Observations d’un véritable assistant | Selon les accès disponibles |
| [6 — MCP et skills](06-mcp-skills.md) | Intégration produit et comportement avec un modèle | Selon les accès disponibles |
| [7 — Adaptation](07-adaptation.md) | Entraînement LoRA d’un LLM sur GPU et rechargement | Seulement pour un accès ou budget réellement manquant |
| [8 — Comparaison personnelle](08-observation.md) | Observation humaine facultative | Oui : l’assistant ne peut pas mesurer à sa place son apprentissage |

Les essais CPU déjà effectués et leurs limites sont détaillés dans les rapports de vérification du dépôt. La présence de ces missions **ne signifie pas** que leurs expériences ont été exécutées. La partie 1 ne demande pas d’essai sur le PC.

Un [modèle de rapport](RAPPORT-TYPE.md) permet de garder des résultats comparables. L’assistant l’adapte aux mesures disponibles, sans remplir les cases manquantes par des estimations non signalées.
